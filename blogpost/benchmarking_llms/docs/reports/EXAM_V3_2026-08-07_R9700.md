# exam_v3 on the R9700 (hopper), 2026-08-07

Six local models, 5 seeds each, 30 attempts. Reasoning ON, `max_tokens 16384`,
`temp 1.0`, `top_p 0.95 / top_k 20 / min_p 0.0`, seeds 42/123/456/789/1011.

Three findings, in order of how much they should change what you do next:

1. **Gemma 4 31B QAT beats the PTQ build of the same size and quant by a wide
   margin** — median 12/13 vs 5/13.
2. **`TestLongOutage/EvictionNotContiguous` is passable.** It was passed 5 times
   here after 0/12 previously. The practical ceiling is **12/13**, not 11/13.
3. **Seed variance dominates the whole table.** One model spans 6–11/13 on seed
   alone. Any exam_v3 ranking built on 2 seeds is mostly noise, including the
   ones already published.

## QAT vs PTQ

Same architecture, same quant format, same context, 17.3 GB vs 20.4 GB on disk.
QAT scored ≥11 in 4 of 5 attempts; PTQ in 2 of 5. Both compiled 5/5, so this is
a reasoning-quality gap, not a code-generation-stability gap.

This is the one result here that is directly actionable: `gemma-31b-qat` is
already configured and is strictly the better default of the two. At n=5 with
this much spread the *size* of the gap is not well determined — the direction is.

## The ceiling is 12/13, and the systematic −1 is real

`TestNewScraperValidation` passed **0 of 22** scored attempts. Combined with the
16/16 from 2026-08-06 and April's best run, that is 38 consecutive failures by
every model ever run here. `prompt.txt` never asks for argument validation; the
only hint is the `(Scraper, error)` return in a signature models are told not to
change. The reference response scores 13/13 only because it adds five guard
clauses nobody asked for. **Every exam_v3 score carries a systematic −1.**

`TestLongOutage/EvictionNotContiguous` is a different story and the runbook's
guess that it was "possibly the same class of problem" is now falsified: it
passed 5/30 here (3× QAT, 1× PTQ, 1× E4B). It is hard, not impossible. Leave it
in.

Fix or drop `TestNewScraperValidation` before publishing anything from exam_v3.

## Seed variance invalidates n=2 rankings

The continuity anchor was run at 5 seeds specifically to test the machine
comparison, and incidentally measured the noise floor:

`qwen-35b-moe-mtp`: 6, 6, 7, 10, 11 — median 7, spread 5 points on a 13-point
scale whose effective ceiling is 12.

The spread within a single model is comparable to the gaps between models. The
guidance in `docs/notes/TODO.md` ("seeds stay at 42/123. Do not add seeds;
scores are near-binary") does not survive this: the scores are not near-binary,
they are high-variance, and n=2 cannot separate models. Reported medians here
are medians of 5 and should not be compared against anyone else's n=2 number
without saying so.

## Machine comparability

hopper's `qwen-35b-moe-mtp` is the same build as the Framework 13's cell B
(Qwen3.6-35B-A3B UD-Q4_K_XL + MTP, 22.85 GB), so it is the only cross-machine
anchor.

- Framework 13, n=2: 7, 5
- hopper, n=5: 6, 6, 7, 10, 11 (median 7)

Three of five hopper draws land inside the Framework 13 range; `{5, 7}` is an
unremarkable two-draw sample from this distribution. **The machines are
comparable.** Note that seeds do *not* transfer across backends — different
llama.cpp build, GPU, and llama-swap version mean identical seeds take different
sample paths — so per-seed agreement was never the right test, only distributional
overlap.

## Throughput

The R9700 is roughly 10× the Framework 13 on this workload: 127 t/s vs 11–12 for
the identical Qwen MoE build, 86 s vs 864–960 s wall. The Framework 13 numbers
were taken under `platform_profile: low-power`, so this overstates the hardware
gap by an unknown amount.

hopper has no ACPI `platform_profile` (desktop/server board), but its CPU
governor is `powersave` — so these numbers are **also** not a
performance-profile measurement. Decode is GPU-bound so the effect should be
small, but neither arm of this comparison was taken under a tuned profile.
Treat both as floors, not as a clean hardware comparison.

Decode splits cleanly by architecture: MoE + MTP 127 t/s, dense 31B 23–25 t/s.
The dense Gemmas are the slowest cells in the table by 3–4×, and the QAT build
is the only one that earns the wait.

**Superseded the same day:** Gemma 4 MTP landed in llama.cpp on 2026-06-07
(PR #23398) and hopper runs b10025, so the dense 31B no longer decodes at 25 t/s.
With the QAT MTP drafter at `--spec-draft-n-max 4` it measures **56.3 t/s**
(69.1% draft acceptance) — 2.23×, which removes the "slowest cell" objection
entirely. The exam_v3 scores above were taken *without* MTP; MTP verifies draft
tokens against the target, so it is lossless and the /13 column is unaffected,
but every `t/s` and `wall_s` for `gemma4-31b-qat-r9700` is now a floor.

## Method notes

- Grader gate: `make-reference-response.py` → `eval.sh` scored **13/13** before
  every run. Nothing here is quoted from an unvalidated evaluator.
- Samplers are now sent explicitly by `exam-driver.go` (`-top-p/-top-k/-min-p`)
  and recorded per-attempt under `sampler` in `result.json`. Previously they came
  from each entry's launch flags: hopper's Qwen MTP entries set
  `top_p 0.95 / top_k 20 / min_p 0.0` and the Gemma entries set nothing
  (llama.cpp defaults `top_k 40 / min_p 0.05`), which would have made this table
  partly a sampler comparison.
- `exam-driver.go` `unload()` now tries `GET /unload` first; llama-swap v211 on
  hopper 404s both POST paths.
- Cells E–J added to `scripts/sweep-exam3-rocmfp4.sh`; docker is now required
  only for cell A.
- Artifacts: `artifacts/results/exam_v3_r9700/`, logs under
  `artifacts/logs/exam_v3_r9700/`.
