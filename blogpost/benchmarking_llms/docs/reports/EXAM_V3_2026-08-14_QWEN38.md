## The 12/13 ceiling is broken

`TestNewScraperValidation` **passed on seeds 42, 456 and 789**.

Runbook §2.3 records that this test failed in 16/16 attempts on 2026-08-06,
failed in April's best 11/13 run, and "has never been passed by any model in
this lab's recorded history" — the basis for the standing claim that every
exam_v3 score carries a systematic −1 and the real ceiling is 12/13.

Qwen3.8-27B is the first model here to pass it. Verified in the raw log:

```
=== RUN   TestNewScraperValidation
--- PASS: TestNewScraperValidation (0.00s)
```

`scraper.go:50-53` shows it emitted the guard clauses the prompt never asks
for (`if source == nil { return nil, fmt.Errorf("source is nil") }`), which is
exactly what the reference response does to reach 13/13.

**§2.3 needs revising.** The ceiling claim is no longer true, and the "subtract
1 from the denominator" guidance now silently inflates this model relative to
the rest of the table.

Its failure profile is also unlike Gemma's: it passes the validation, hang and
load tests, and fails the whole outage/buffer family
(`TestNoLossAcrossTransitions`, `TestShortOutageNoLoss`, all three
`TestLongOutage` subtests). That is a coherent single weakness — buffering
across an outage — not scattered breakage.

## The un-drafted control arm

An earlier sweep the same evening ran the identical model, quant, samplers,
budget and seeds with `--spec-type` unset, so the MTP head loaded and was never
used. Kept because it is an accidental controlled pair.

| | scores | med | compiled | t/s | wall s |
|---|---|---:|---:|---:|---:|
| un-drafted | 1, 0, 5, 5, 0 | 1 | 3/5 | 25.2 | 489 |
| MTP | 7, 0, 6, 6, 7 | 6 | 4/5 | 42.5 | 294 |

Raw: `artifacts/results/exam_v3_r9700_qwen38/`.

This lab's standing assumption — stated in `sweep-exam3-rocmfp4.sh`'s
`cell_spec` comment — is that "MTP is lossless for scoring: it moves t/s and
wall_s, not /13". These two arms disagree with that.

Tested, and the result is **not conclusive**:

- Mann-Whitney U, one-sided: **p = 0.044**
- Welch t-test: **p = 0.126**

n=5 per arm, near-binary scores, one shared 0. Two tests disagreeing is what
underpowered data looks like. Speculative decoding consumes RNG differently, so
identical seeds take different sample paths — the gap may be nothing more than
a different draw, and this lab has already documented that seeds do not
transfer across backend changes.

**Hypothesis, not a finding:** llama.cpp's speculative acceptance rule may bias
toward higher-probability tokens, acting as an effective temperature reduction,
which at `temp 1.0` on a coding task would help. If that is real, every
MTP-vs-non-MTP comparison in this lab's tables carries a confound.

**Cheapest test:** re-run the un-drafted arm on five fresh seeds. Near median 1
again → real effect. Near median 6 → it was variance. ~25 min. A second
replication is available for free: `qwen-27b` (3.6, no MTP) against
`qwen-27b-mtp`, whose 0,6,6,0,0 is already on record.

## A harness failure mode worth recording

In the un-drafted arm, `seed123` scored 0/13 with `compile:FAIL`, and it was
**not a model result**. Its `response.txt` opened mid-sentence in reasoning
prose, contained **57** bare ``` fences, ended mid-function, and consumed
exactly 16,384 tokens — the `max_tokens` cap. That is thinking sitting in the
`content` field; `exam-driver.go:148` reads only `Message.Content`.

Fence count discriminates cleanly: genuine attempts have exactly **2** (one
```go block, opened and closed). All five MTP-arm attempts had 2 — the spill
did not recur.

This is a **new variant of runbook §2.2.1**, whose non-negotiable is
"`max_tokens` MUST exceed `--reasoning-budget`". Here it does — 16384 > 8192 —
and is still not sufficient. §2.5's decision table needs a fourth row:

> `response.txt` non-empty but is reasoning prose, `tokens` at exactly the cap,
> fence count >> 2 → reasoning spilled into `content`. Harness-class, not a
> model result.

## Caveats

- n=5, single attempt per seed. Seed variance dominates exam_v3; a one- or
  two-point median difference is not a ranking.
- `TestLongOutage/EvictionNotContiguous` failed in all five attempts here,
  consistent with its 0/12 history. Still undiagnosed.
- Samplers are Unsloth's published *thinking-mode* set for Qwen3.8
  (temp 1.0 / top_p 0.95 / top_k 20 / min_p 0.0, presence 0.0, rep 1.0), which
  coincides exactly with this table's standing exam_v3 settings. Nothing was
  changed to accommodate the model.
- No `--mmproj` is loaded on this entry; `qwen-27b-mtp` does load one. That is
  a VRAM difference between entries, not a scoring one.
